## Overview

Before memory can be analyzed, it has to be acquired — and the quality of that acquisition determines how much forensic value the analysis phase can extract later. For a SOC/blue team analyst, this is the step that sits between "I suspect something is live in memory" and "I have a forensically sound artifact I can run through Volatility." Get the timing, tooling, or format wrong, and the evidence is gone or unusable — memory content changes constantly and can't be recaptured after the fact.

This room walks through the decision points behind any memory acquisition (what to capture, which tool, when, how to preserve integrity) and then applies them hands-on across Windows, Linux, hypervisors, and cloud platforms.

## Task 2 — Techniques, Tools, and Best Practices

Before acquiring memory, an IR playbook should already define: which acquisition technique, which tool, timing, what part of memory to focus on, and how integrity will be ensured.

### Selecting the right memory part

🔴 The scope of the capture should match the indicator. A full memory dump for a suspected C2-connected malware infection; a process dump when a single process shows unusual CPU/memory use; the `hiberfil.sys` file if the system was put into hibernation instead of powered off (e.g. to avoid tipping off an insider-threat suspect).

| Type | Captures | Use Case |
|---|---|---|
| Full Memory Dump | Entire physical RAM | Full forensic analysis, malware behavior, CTI |
| Process Dump / Core Dump | Single process (heap, stack, code, modules) | Detect malware injection, behavior analysis |
| Memory Region Dump | Specific region of a process (stack, heap, injected code) | Extracting malware/shellcode |
| Pagefile/swapfile | Swapped-out virtual memory (`pagefile.sys` / `\swapfile`) | Memory from recently terminated/suspended processes |
| Hibernation File Dump (Windows only) | RAM snapshot from sleep (`hiberfil.sys`) | Full capture when live memory isn't available |
| VM Memory Dump | Volatile memory of a lab machine | Safe malware testing, replayable incident analysis |

### Choosing the file format

| Format | Notes |
|---|---|
| `.raw` / `.mem` | Raw physical memory, cross-platform, preferred for tool compatibility |
| `.dmp` | Windows built-in dump format |
| `.vmem` / `.vmsn` / `.vmss` / `.bin` / `.sav` | Hypervisor snapshot/suspend states; `.sav` needs conversion before analysis |
| `.core` | ELF-formatted process dump (Linux, via `gcore`) |
| Expert Witness Format | Generated by EnCase |
| `.lime` | Structured full memory dump from LiME |

### Choosing the acquisition technique

- **Local** — external storage plugged into the target; needs physical access
- **Remote** — captured then transferred over the network; useful for headless/remote systems
- **Hardware** — dedicated PCIe card, OS-independent, but costly
- **RAM freezing** — physically freezes RAM to slow decay, buying time to move modules to another system

💡 Administrator privileges are required for a complete dump. Remote transfer risks the receiving system getting compromised too; local storage devices can themselves become compromised — use a disposable system for initial analysis. Hardware acquisition cost should match the system's importance.

### Tools

| Commercial | Free |
|---|---|
| EnCase Forensic | FTK Imager |
| CaptureGUARD (PCIe & ExpressCard) | Magnet RAM Capture |
| F-Response | DumpIt |

Selection criteria: integrity, compatibility, speed/scalability, compliance, cost, and forensic noise introduced.

### Timing

🔴 Memory is a snapshot of a single moment — timing decisions directly affect what evidence is recoverable. Quick action on a lateral-movement host or a fileless-malware alert can capture remote sessions, compromised credentials, malicious PowerShell, or C2 IPs. Waiting too long — as in a case where a user reboots a system before it can be imaged — can mean losing exfiltration evidence entirely. Avoid capturing during high-volatility periods (bootup, virus scans, backups).

## Task 3 — Memory Acquisition on Windows

**Lab:** Windows Server 2019 with FTK Imager and SysinternalsSuite pre-installed.

All captures in this task target compatibility with **Volatility**, which supports raw/padded physical memory, Firewire, EWF, 32/64-bit Windows crash and hibernation dumps, MachO, VirtualBox core dumps, VMware `.vmss`/`.vmsn`, HPAK, LiME, and QEMU dumps.

💡 After every capture, generate an MD5 hash to preserve integrity — always analyze a copy, never the original, and use the hash to confirm the copy is identical.

### Process memory dump (procdump64.exe)

🔴 `lsass.exe` manages authentication, tokens, and credentials — it's a frequent target for credential-theft tools like Mimikatz, making it a high-value process to dump during an investigation.

```powershell
PS C:\TMP\SysinternalsSuite> .\procdump64.exe -ma lsass.exe C:\TMP -accepteula

ProcDump v11.0 - Sysinternals process dump utility
Copyright (C) 2009-2022 Mark Russinovich and Andrew Richards

[13:45:44] Dump 1 complete: 47 MB written in 0.5 seconds
```

- `-ma` — full memory content dump (default `-mm` is a minidump, useless for malware analysis/credential extraction)

## Task 4 — Memory Acquisition on Linux

**Lab:** Ubuntu desktop VM.

Same decision process as Windows; captures must also stay Volatility-compatible, and integrity is verified with `md5sum`.

### Full memory capture (LiME)

Install (not needed on the pre-configured lab VM):
```bash
sudo apt update
sudo apt install -y git build-essential linux-headers-$(uname -r)
git clone https://github.com/504ensicsLabs/LiME.git
cd LiME/src
make
```

Capture:
```bash
cd LiME/src
sudo insmod lime-6.8.0-1027-aws.ko "path=/tmp/ubuntu-150000-22042025.lime format=lime"
```

- `sudo insmod lime-6.8.0-1027-aws.ko` — loads LiME into the kernel
- `path=/tmp/ubuntu-150000-22042025.lime` — output path, naming template `HOSTNAME-HHMMSS-DDMMYYYY.lime`
- `format=lime` — output format

```bash
md5sum tmp/ubuntu-150000-22042025.lime
0ef7140f0c0cabd6c4ef76c708f2324f  /tmp/ubuntu-150000-22042025.lime

sudo rmmod lime
```

💡 `rmmod lime` must be run before every new capture to unload any previously loaded LiME module.

### Process memory dump (gcore)

```bash
ps aux | grep bash
ubuntu      6506  0.0  0.2   5892  4096 pts/0    Ss   Apr11   0:00 bash
ubuntu     34136  0.0  0.1   3528  1792 pts/0    S+   13:57   0:00 grep --color=auto bash

sudo gcore -o /tmp/BASH-130000-10042025 6506
```

```bash
md5sum /tmp/BASH-130000-10042025.6506
b1baa84b8f1e725f1a45795465ba710c  /tmp/BASH-130000-10042025.6506
```

### Crash dump configuration

**Kernel crash dump** — enabled by default from Ubuntu 24.10 onward; the lab VM runs 24.04 so it was pre-configured:
```bash
cat /proc/cmdline   # check for crashkernel=... to confirm it's enabled
sudo apt install kdump-tools -y
sudo -reboot
sudo kdump-config show
```

**Process crash dump** — disabled by default on most distros. Two pieces needed for full Ubuntu Desktop coverage:

```bash
# systemd-managed processes
sudo mkdir -p /etc/systemd/system.conf.d
sudo nano /etc/systemd/system.conf.d/core-dumps.conf
# [Manager]
# DefaultLimitCORE=infinity
sudo systemctl daemon-reexec

# interactive sessions / user processes
ulimit -c unlimited
sudo nano /etc/sysctl.d/60-core-pattern.conf
# kernel.core_pattern = /var/crash/core.%e.%p.%t
# fs.suid_dumpable = 1
sudo mkdir -p /var/crash
sudo chmod 1777 /var/crash
```

💡 Ubuntu Desktop's built-in `apport` service also catches crashing-process core dumps and writes `.crash` files (stack trace, process info, loaded libraries, partial memory) to `/var/crash` — note it captures partial, not full, memory content.

### Q&A

**Modify the following command to ensure the memory dump is in the .raw format and is accessible over TCP port 5555:** `sudo insmod lime-6.8.0-1027-aws.ko "path=/tmp/memdump.lime format=lime"`

**LiME includes a parameter to create a hash immediately after capturing the memory. Modify the following command and ensure a MD5 hash is calculated:** `sudo insmod lime-6.8.0-1027-aws.ko "path=/tmp/memdump.lime format=lime"`

## Task 5 — Memory Acquisition on Virtual Machines and Cloud Environments

Two approaches for hypervisors/cloud: log into the VM and use standard Windows/Linux techniques, or use the hypervisor/cloud platform's built-in tooling to extract memory without touching the VM directly. This task focuses on the latter where available.

### Microsoft Hyper-V

```powershell
PS C:\Users\administrator> get-vm | FT VMId, VMName

VMId                                  VMName
c5f1b464-ffea-4904-bc7b-974c74b10159  Ubuntu 22.04 LTS

PS C:\Users\administrator> get-vm -Id c5f1b464-ffea-4904-bc7b-974c74b10159 | Checkpoint-VM
PS C:\Users\administrator> Get-VMSnapshot -VMName 'Ubuntu 22.04 LTS' | FT Id,Name,Path
PS C:\Users\administrator> cp C:\ProgramData\Microsoft\Windows\Hyper-V\Snapshots\97DBBAE5-3F91-4E5E-B177-FBB970E8703E.VMRS C:\temp\hostname-17-04-2025.VMRS
PS C:\Users\administrator> Get-FileHash -Algorithm MD5 -Path C:\temp\hostname-17-04-2025.VMRS
Algorithm Hash                             Path
MD5       E1BA77075C7C832CC96E43DB8E8F98E8  C:\temp\hostname-17-04-2025.VMRS
```

Process: checkpoint/save the VM → copy the `.vmrs` file → hash it → process with Volatility's `windows.hyperv` plugin.

### vSphere

Take a snapshot → copy the `.vmsn` file from the datastore → hash it. Volatility supports `.vmsn` natively, no conversion needed.

task5-01.gif

### KVM

```bash
virsh list
virsh dump vmname /path/to/dump.raw --memory-only
md5sum memdump.raw
```

### VirtualBox

```powershell
PS C:\Program Files\Oracle\VirtualBox> .\VBoxManage.exe list runningvms
"Kali_purple" {9a969c90-7ab0-4b9b-893d-48c70fa42ee5}
PS C:\Program Files\Oracle\VirtualBox> .\VBoxManage.exe debugvm "Kali_purple" dumpvmcore --filename C:\temp\kali_memdump.elf
PS C:\Program Files\Oracle\VirtualBox> Get-FileHash -Algorithm MD5 -Path C:\temp\kali_memdump.elf
Algorithm Hash                             Path
MD5       1833B5B07C8E43A6E011919934AFB049  C:\temp\kali_memdump.elf
```

Volatility supports `.elf` dumps natively.

### Cloud platforms

🔴 Neither Azure nor AWS provides built-in memory acquisition tooling, largely due to shared hardware — direct interaction with the VM (standard OS-level techniques from Tasks 3–4) is the recommended path.

Alternate method:
1. Configure a full memory crash dump on the host
2. Trigger a manual crash via the cloud platform
3. Detach the disk holding the crash dump
4. Attach the disk read-only to an analysis VM (same or different tenant)
5. Optional: export the disk for use in a different tenant

💡 Microsoft's **AVML** (Acquire Volatile Memory for Linux) simplifies Azure Linux VM acquisition — runs as a standalone binary with no installation or kernel loading required. Linux-only.

## Task 6 — Challenges with Memory Acquisition

| Challenge | Detail |
|---|---|
| Anti-forensic techniques | Attackers may encrypt memory content or interfere with acquisition tools |
| Timing | Memory changes constantly — track IOAs/IOCs to time the capture |
| (Physical) Accessibility | Data center servers may need special access approval |
| No admin rights | Full capture requires admin rights at host, domain, or cloud resource-group level |
| Lack of an ISMS | Asset Management (hostname, IP, OS, users, location, criticality, operating hours, baseline config/behavior) is a prerequisite for effective acquisition |
| No transparent IR process | Memory acquisition must be built into the incident response plan |

## Key Takeaways

- Acquisition quality is the ceiling for everything analysis can later recover — get timing and scope wrong and the evidence is unrecoverable
- Match the capture type to the indicator: full dump for active malware/C2, process dump for a single suspicious process, hibernation file when the system is asleep rather than off
- Always validate format compatibility with the downstream analysis tool (Volatility here) before choosing an acquisition tool
- Hash every capture immediately (MD5 in this room) and always work from a copy, never the original
- Hypervisor/cloud acquisition favors built-in snapshot tooling where available (Hyper-V, vSphere, KVM, VirtualBox); cloud platforms are the exception and generally require direct OS-level interaction or the crash-dump/disk-detach workaround
- `lsass.exe` process dumps are a recurring credential-theft target worth prioritizing in Windows investigations
